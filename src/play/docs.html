the shape of a file

A diagram is a short text file, one diagram per file, usually saved as .ksd. It reads top to bottom: first say what kind of diagram it is and what it shows, then list the parts, then say how they connect.

diagram flowchart
title After review, a request takes exactly one of two paths

start begin
process review "review request"
decision ok "approved?"
process schedule "schedule the work"
process notify "notify requester"
end done

begin -> review
review -> ok
ok -> schedule : yes
ok -> notify : no
schedule -> done
notify -> done

  • One statement per line. Blank lines are ignored. A line starting with # is a comment.
  • Leading and trailing spaces don't matter, so indent however you like. Indenting the inside of a block is a habit, not a rule.
  • Header lines come first, then nodes and edges in any order. Once the first node or edge appears, header words stop being special.
  • Some things open a block: a line ending in {, then the lines inside, then } on its own line. Boundaries, partitions, classes with members, use-case descriptions and the layout block all work this way.
  • The parser is strict on purpose. A line it can't read is an error, never a guess. The playground marks every bad line and keeps showing the last version that could be read, so a typo never becomes a wrong picture.

the header

Everything before the first node or edge. Two lines are required; the rest are optional.

ids, labels and options

ids

  • A letter, then letters, digits, - or _: review, pay-fee, step_2.
  • Unique within the file, boundaries, partitions and classes included. A repeat is an error, not a replacement, because ids are also what the strokes are seeded from.
  • Ids are what edges refer to, so keep them short and typeable. The label is what the reader sees.

labels

  • Double quotes: action pay "pay the fee".
  • \n breaks a line inside a node: process check "check the\npaperwork".
  • \" puts a quote inside a label; \\ is a backslash.
  • Leave the label off and the id becomes the label with - and _ turned into spaces: action order-laptop reads "order laptop". A class keeps its id exactly as typed.
  • No em dashes.

options after the label

optionmeaning
left or rightWhich side of the system an actor stands on. Default left. Only actors use it.
at X YPin the node's center at X, Y inches, overriding the automatic layout for that node only. A place line in the layout block does the same from the end of the file, and that is where the draw tab saves a drag. A node that already has at on its own line keeps it there.
size W HFix the node's width and height in inches instead of sizing it to its text. Both must be above zero. The label wraps inside. A size line in the layout block does the same.
 
actor clerk "Permit clerk" right
process review "review request" at 4 2.5
process file "file the form" at 4 4 size 2.2 0.8

boundaries

A use-case diagram puts its use cases inside the system they belong to. A boundary line opens a block: an id, the system's name in quotes, an opening brace, then the use cases, then a closing brace on its own line.

boundary portal "Permit portal" {
  use-case apply "apply for permit"
  use-case pay "pay fee"
}
  • One level only. Boundaries don't nest.
  • The boundary's id counts as an id, so no node can reuse it.
  • Actors go outside. The parser will let you put one inside, and the notation check reports it (UC-ACTOR-INSIDE), which is the right behavior when the lesson is about why actors go outside.
  • A use case left outside any boundary draws in a column to the right of it and is reported (UC-OUTSIDE-BOUNDARY).

partitions (swimlanes)

An activity diagram can say who does each step. A partition line opens a block, written like a boundary: an id, the participant's name in quotes, an opening brace, the nodes that participant does, then a closing brace on its own line. Each partition is drawn as a lane with its name in a header.

partition customer "Customer" {
  start begin
  action place "place order"
}
partition sales "Sales" {
  action check "check payment"
  end done
}

begin -> place
place -> check
check -> done
  • lane and swimlane mean the same as partition. Tidy writes partition.
  • Partitions belong to activity diagrams and flowcharts. In a use-case or class diagram they are an error.
  • Lanes are drawn in file order. Where a node is declared decides its lane; edges can go anywhere in the file and cross lanes freely.
  • One level only. A partition can't hold another partition or a boundary, and a boundary can't hold a partition.
  • The partition's id counts as an id, so no node can reuse it.
  • Once a diagram has partitions, every node belongs in one. The check reports a node left outside (ACT-PARTITION-OUTSIDE; notes are let off), a lane with nothing in it (ACT-PARTITION-EMPTY) and a diagram with a single lane (ACT-PARTITION-SINGLE).
  • How wide a lane is and where the lanes start can be set in the layout block, which is where the draw tab saves a dragged lane divider.

lanes as rows

Lanes run along the flow. By default that means columns, read top to bottom. A lanes horizontal line in the header turns them into rows, read left to right.

diagram activity
id file-form
title The clerk only files a form the resident has signed
lanes horizontal

partition resident "Resident" {
  start begin
  action sign "sign form"
}
partition clerk "Clerk" {
  action file "file form"
  end done
}

begin -> sign
sign -> file
file -> done

edges

<from> <operator> <to> [: label]

Spaces around the operator are required: a -> b, not a->b.

writemeaningdrawn as
a -> b or a --> bcontrol flow: a, then b. In a use-case diagram the check reads it as a directed association, which it then tells you to undirectsolid arrow
a -- bassociation: this actor uses this use caseplain line, no head
a -include-> b«include»: doing a always includes doing b. Points from the base use case to the included onedashed arrow with an open head and the «include» label
a -extend-> b«extend»: a sometimes adds to b. Points from the extension to the base it extendsdashed arrow with an open head and the «extend» label
a ..> ba proposed or hypothetical path, as opposed to what actually happensdashed arrow

That table is for flowcharts, activity diagrams and use-case diagrams. Between classes the same strokes mean class relationships, and there are more of them: see classes. -include-> and -extend-> are an error in a class diagram, and the class-only operators are an error everywhere else.

branch labels

Anything after a colon is the edge's label. Every exit from a decision needs one; the check won't pass a diamond with an unlabeled branch.

ok -> schedule : yes
ok -> notify : no
checked -> refund : [approved]

Flowcharts say yes and no; activity diagrams use guards in square brackets. Labels sit beside the line, never on it, and move to the other side by themselves if something is in the way.

edge ids

Edges are numbered e1, e2, ... in file order. You'll see those ids in findings ("edge e2") and as data-name on the SVG groups.

edges to nothing

An edge whose end names an id that was never declared is kept, not dropped: the parser adds a warning (PARSE-UNKNOWN-NODE), the notation check reports STRUCT-DANGLING-EDGE, and the drawing skips it. Again, that's so a lesson can show the mistake.

classes

A class diagram (diagram class) shows what things are made of and how they relate. Its nodes are classes and interfaces, and their lines carry a little more than other nodes do.

[abstract] class|interface <id> ["label"] [<<stereotype>>] [at X Y] [size W H] [{]
class Square
class Circle {
  -radius: float
  +area(): float
}
interface Drawable {
  +draw(canvas: Canvas): void
}
abstract class Shape {
  #origin: Point
  +area(): float {abstract}
}
class Repo "Order repository" <<service>>
  • class or interface, then an id. The id is the name on the box, exactly as typed: LineItem stays "LineItem". A quoted label after the id replaces it.
  • abstract in front marks an abstract class. It is drawn with {abstract} under the name.
  • A stereotype goes after the label as <<service>>, or with real guillemets as «service», and is drawn above the name. Tidy writes the first spelling. An interface always shows «interface» there, so a stereotype of its own is kept in the text but not drawn.
  • A class with members ends its line with {, lists one member per line, and closes with } on its own line. A class without members is just its line, with no braces at all.
  • at X Y and size W H work as on any node. left and right don't apply.
  • A note works here as in any diagram.

members

[+|-|#|~] <name>[: Type] [{static}] [{abstract}]
[+|-|#|~] <name>(parameters)[: Type] [{static}] [{abstract}]

The first form is an attribute, the second an operation; the parentheses make the difference. Attributes are drawn in the upper compartment and operations in the lower one, each in file order.

markvisibility
+public
-private
#protected
~package
  • The mark is optional. A member without one is drawn without one.
  • The name is one word. The type is whatever follows the colon, kept as written, so -total: Money = 0 carries its default value along.
  • The parameters are whatever sits between the parentheses, kept as written: +pay(amount: Money): Receipt.
  • {static} underlines the member. {abstract} is drawn after it. Either can be written before or after the member; tidy puts them at the end.
  • A space after the mark is fine (+ name: String), with one exception. A line that starts with # and a space is still a comment, so write a protected member tight: #origin: Point.
  • No em dashes.

relationships

writemeaningdrawn as
a -- bassociation: instances of a and b are linkedplain line
a --> b or a -> bdirected association: linked, and navigable toward bplain line with an open arrowhead at b
a --|> bgeneralization: a is a kind of b. The triangle points at the parentsolid line with a hollow triangle at b
a ..|> brealization: a implements the interface bdashed line with a hollow triangle at b
a o-- baggregation: a is a whole and b is one of its parts. The diamond sits on the wholeline with a hollow diamond at a
a *-- bcomposition: b is a part that lives and dies with aline with a filled diamond at a
a ..> bdependency: a uses b without holding a link to itdashed line with an open arrowhead at b

Four of these can be written from the other end. They mean the same with the ends swapped, and tidy rewrites them in the form above:

writesame as
a <|-- bb --|> a: b is a kind of a
a <|.. bb ..|> a: b implements a
a --o bb o-- a: b is the whole
a --* bb *-- a: b is the whole

The automatic layout puts a parent ahead of its children (above them, when the diagram runs down) whichever way the line was written. A label after a colon names the relationship, as on any edge.

multiplicities and role names

Quoted text between an end and the operator belongs to that end. It says how many, what the end is called in the relationship, or both.

Customer "1" -- "0..*" Order : places
Order "1" *-- "1..* items" LineItem
Team "0..1 lead" --> "1" Person
  • A multiplicity is *, a number, or a range: 1, 0..1, 1..*, 2..5.
  • Words after the multiplicity are the role name: "1..* items". Text that doesn't start with a multiplicity is all role name: "owner".
  • The multiplicity is drawn on one side of the line's end and the role name on the other.
  • Either end can go without. The check asks for a multiplicity at both ends of every association (CLASS-MULTIPLICITY), because the story usually depends on how many.
  • Only class diagrams have these. Anywhere else they are an error.

use-case descriptions

A use case can carry its written description: the goal, who starts it, the steps. A describe block holds it. Nothing in the block is drawn. It travels with the diagram, the draw tab shows it in the properties panel, and the check compares it with the picture.

diagram use-case
id permit-apply
title A resident applies for a permit, and paying the fee is always part of it
narration Apply for permit includes pay fee.

actor resident "Resident"
actor bank "Payment provider" right
boundary portal "Permit portal" {
  use-case apply "apply for permit"
  use-case pay "pay fee"
}

resident -- apply
bank -- pay
apply -include-> pay

describe apply {
  goal Get a permit without a visit to the office
  primary resident
  supporting Payment provider
  trigger The resident opens the permit form
  pre The resident has an account
  main 1. The resident fills in the form
  main 2. The resident pays the fee
  main 3. The portal confirms the application
  alt 2a. The payment fails: the portal keeps the form as a draft
  post The application is waiting for review
  related pay (include)
}

Each line inside is a field word, then text to the end of the line, with no quotes.

fieldhow manywhat it holds
goalonewhat the actor wants out of it
primaryonethe actor who starts the use case, by id or by label. The check looks for that actor in the diagram and for its association with this use case (UC-DESCRIBE-PRIMARY)
supportingone line eachanother actor that takes part
triggeronethe event that starts it. It shouldn't also appear as a pre line (UC-DESCRIBE-TRIGGER)
preone line eachsomething that already holds before it starts
mainone line eacha step of the main success scenario. Number the steps yourself. A description without any gets a suggestion (UC-DESCRIBE-MAIN)
altone line eachan alternative or an exception to a step
postone line eachsomething that is true afterwards
relatedone line eachanother use case and how it relates
  • Every field is optional and they can come in any order. Lines of the same field keep their order.
  • A field that takes one value and is written twice keeps the last one.
  • A field word needs text after it.
  • The block goes after the line that declares its use case, names a use case and nothing else, and each use case gets one block at most.
  • Only use-case diagrams have describe.
  • No em dashes.

build-up steps

A diagram can reveal itself one click at a time, the way a slide builds while someone talks. Put a step <n> line in the file and everything after it, nodes and edges alike, belongs to that step until the next step line. Everything before the first step line is step 0 and is always shown.

start begin
action accept "accept offer"
begin -> accept

step 1
fork split
action laptop "order laptop"
action badge "print badge"
accept -> split
split -> laptop
split -> badge

step 2
join wait
action first "first day"
end done
laptop -> wait
badge -> wait
wait -> first
first -> done
  • The embed opens at step 0 with back, next step and show all under the figure. Left and right arrow keys work when the figure has focus.
  • Hidden parts stay in the page but are marked hidden for screen readers until their step.
  • Give each step one idea, in the order the narration introduces them. Steps are for when the order of parts is the lesson. A diagram said all at once doesn't need them.
  • Step numbers don't have to be consecutive, but the controls count the highest one, so gaps just make empty clicks.
  • Nothing ever advances by itself.
  • Steps are written here, in the text. The draw tab keeps them but doesn't change them.

the layout block

Everything so far says what the diagram means, and where things sit is worked out for you. When you move, resize, reroute or restyle something in the draw tab, that one choice is written as a line in a layout block at the end of the file. So the text is still the whole diagram: a link, an embed and a saved file all carry the arrangement.

diagram flowchart
id manual
title A draft is reviewed and either published or sent back
start begin
process draft "write draft"
decision ok "ready?"
process publish "publish"
end done

begin -> draft
draft -> ok
ok -> publish : yes
ok -> draft : no
publish -> done

# layout: written by the draw view. Delete a line to hand that part back to automatic layout.
layout {
  place publish 3.4 3.2
  size publish 1.8 0.7
  place done 3.4 4.5
  route ok -> draft elbow from left to left via -0.9 3.03, -0.9 1.6
  style ok -> publish color accent weight bold
  style publish fill wash
}
  • The draw tab writes this block and keeps it current. You can edit it by hand; you rarely need to.
  • Delete a line and that one thing goes back to automatic layout. Delete the whole block and the whole diagram does.
  • Anything the block doesn't name is still placed for you.
  • It opens with layout { and closes with } on its own line, and it can't sit inside another block.
  • Numbers are inches, with decimals. X runs right and Y runs down.
  • A line that names something the file doesn't declare is kept, with a warning (LAYOUT-UNKNOWN-REF), and does nothing. Renaming a node by hand never breaks the file.

lines about nodes

linemeaning
place <id> X YPin the node's center at X, Y. The same as at X Y on the node's own line; a node takes one or the other, once.
size <id> W HThe node's width and height, in place of the size its text asks for. Both above zero.
style <id> [fill F] [color C] [weight W]How the node is drawn. At least one of the three. fill is none (see-through), page (the page color, the default) or wash (a pale tint). color and weight are listed below.
lane <id> <thickness>A partition's thickness across the flow: the width of a column lane, the height of a row lane. Above zero. Without it the lane is as thick as its contents need.
pool [at X Y] [length L]The lanes as a group. at is the corner where the first lane starts. length is how far the lanes run along the flow, at least; they still grow to hold what is in them.

lines about edges

linemeaning
route a -> b straight|elbow [from <side>] [to <side>] [via X Y, X Y]The edge's path. straight runs point to point; elbow runs in right-angled segments. from and to say which side of each node it leaves and arrives at: top, right, bottom or left. via lists the points it passes through, separated by commas, and comes last.
label a -> b <t> <dx> <dy>Where the edge's label sits: t is how far along the path, from 0 at the start to 1 at the end, and dx, dy move it off that point, in inches.
style a -> b [color C] [weight W]How the edge is drawn. At least one of the two.

Colors are the theme's pens, never a hex value, so a styled diagram still follows light and dark: ink (the default), ink-2 (graphite), accent, accent-strong and terra. Weights are thin, normal and bold.

naming an edge

A layout line points at an edge by writing it again: its two ends and its operator, without the label. When several edges join the same two nodes with the same operator, #2 after the ends picks the second one in file order, #3 the third.

process a
process b
a -> b : first try
a -> b : second try

layout {
  route a -> b #2 elbow from right to right
  label a -> b 0.5 -0.6 0
}

The first line routes the second edge around the right-hand side. The second moves the first edge's label to the left of the middle of its line.

a use-case diagram with include and extend

  use-case apply "apply for permit"
  use-case track "track status"
  use-case review "review application"
  use-case pay "pay fee"

resident -- apply

clerk -- review

Swap the include line to pay -include-> apply and the check reports UC-INCLUDE-DIRECTION with high confidence, because the narration says which way it goes.

a class diagram with an interface and inheritance

diagram class
id shapes
title Every shape can report its area; circles and rectangles are kinds of shape

interface Drawable {
  +draw(canvas: Canvas): void
}
abstract class Shape {
  #origin: Point
  +area(): float {abstract}
  +moveTo(p: Point): void
}
class Circle {
  -radius: float
  +area(): float
}
class Rectangle {
  -width: float
  -height: float
  +area(): float
}
class Square

Shape ..|> Drawable
Circle --|> Shape
Rectangle --|> Shape
Square --|> Rectangle

Change Shape ..|> Drawable to Shape --|> Drawable and the check reports CLASS-GENERALIZATION-INTERFACE: a class implements an interface, it doesn't inherit from one.

writing a diagram that teaches

  • Title the finding. The title is the sentence a reader should take away. If you can't write it, the diagram may not need to exist.
  • Pick the type by the claim. Steps with choices are an activity diagram or a flowchart. Who uses the system for which goals is a use-case diagram. What things are made of and how they relate is a class diagram. A use-case diagram has no order and no decisions; if you find yourself drawing "then" between ovals, it's a flow.
  • Paste the narration in. The check reads it. It's the cheapest way to catch a fork where the script says "either", or an «include» pointing the wrong way.
  • Label every branch. An unlabeled exit from a diamond is the most common mistake in student flowcharts, and the check won't pass it.
  • Use cases are verb phrases. "place order", not "orders". A one-word noun gets a suggestion.
  • Lanes are for hand-offs. Use partitions when who does a step is part of the lesson. One lane on its own says nothing.
  • Say how many. An association between classes usually matters because of its multiplicities. Write them at both ends.
  • Keep it to about eight nodes. More than that, split it, or use steps so each click has one idea.
  • Don't draw what the lesson doesn't say. No actors, forks or boundaries added to look more formal.
  • A wrong diagram on purpose is fine. Write it, leave the check panel off on the lesson page, and let the narration do the correcting. The check is for you, not the reader.

the notation check

Every diagram is reviewed with the same rules the slide reviewer uses on the videos, so a diagram gets the same verdict on the site as in a deck. The result is a status and a list of findings.

statusmeans
passno findings
pass with notesonly minor findings or suggestions
needs changesat least one major finding
blockeda critical finding: the diagram teaches the wrong notation

Each finding has a severity, a rule id, where it is, what's wrong, why it matters, and the smallest fix. The check never stops the drawing; a blocked diagram still renders. In the playground the panel is always on; in an embed it's off unless the page asks for it.

Before grading, the check works out what family the structure actually looks like (flow, use case, data, and so on) from the kinds of nodes and edges, and compares that with the claimed type.

Partitions, class members, class relationships and use-case descriptions are newer than the slide reviewer. Their rules are checked here, by the same conventions, until the reviewer has them too.

the layout check

After drawing, the figure is checked on a raster of its real geometry, the same way the slide reviewer checks a deck. The playground shows it always; an embed shows it with qa=1.

codelevelwhat it catches
LINE_THROUGH_TEXTerrorA stroke inside a label's clearance zone (the label's box plus a small margin). Labels keep that zone clear by moving to the other side of their line.
TEXT_OVERLAPerrorTwo labels overlapping.
CLIPerrorInk or a label outside the frame.
SMALL_KALAMwarningHandwriting under 18 px, which Kalam doesn't survive.
PHONE_LEGIBILITYwarningA label that would fall under 13 px on a narrow screen. The figure refuses to shrink that far and scrolls sideways instead.

The layout is automatic until you say otherwise. A shorter label or a step split usually clears a collision. When it doesn't, drag the shape, the line or the label in the draw tab, which writes the fix into the layout block.

A line the parser can't read is an error, and the message says which line. The playground underlines every bad line and keeps the last good figure on screen; an embed shows the first error in place of the figure. These are all of them.

what it won't do yet

  • Four families: flowchart, activity, use-case and class. Sequence, state and ERD have their rules in the check already; the text format for them comes later.
  • No freehand drawing, ever. Shapes are predefined and the pen only renders them.
  • The draw tab places, names, connects, resizes and drags shapes, and writes the result back as this text. What you arrange by hand goes into the layout block. "let it find its own place" hands one shape back to the automatic layout, and "tidy up" hands back as many as you choose.
  • No edge from a node to itself. It parses, the check reports it, and nothing is drawn.
  • No lanes inside lanes, and no notes attached to a specific node.
  • No colors of your own. A style line picks from the theme's pens, by design.
  • No saving to an account. The link is the file.
